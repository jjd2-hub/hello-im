# 消息推送契约

> 版本:**v0.1(草案,待三方确认)**
> 适用:`im-platform` / `im-client` / `im-server`
> 对应代码:`im-common` 下的 `constant/RedisKey`、`enums/IMCmd`、`enums/ClientType`、`enums/ChatType`、`model/IMPushMessage`

---

## 0. 这份文档解决什么问题

三个模块由不同的人写。如果各自"猜"推送怎么做,联调时几乎必然出现:

- 队列 key 命名不一致 → 消息投进去,没人消费
- 信封字段名或时间戳单位不一致 → 反序列化失败 / 时间错乱
- 边界不清 → im-server 开始查数据库、判断好友关系,platform 的数据权威被架空

所以先把接口钉死:**数据怎么放、谁写谁读、谁明确不做什么。**

> 大部分决策已由参考项目 box-im 定下(其 README 的"消息推送方案"一节)。本文档的工作是把它落到本项目的具体 key 名与字段上,并补齐 box-im 没写死的部分。

---

## 1. 角色与边界

| 模块 | 干什么 | 明确**不**干什么 |
|---|---|---|
| **im-platform** | 业务规则 + 数据权威。落库、判断好友/群成员、算未读、对外 REST | 不管理 WebSocket 连接 |
| **im-client** | 与 im-server 通信的**推送 SDK**。查连接位置、把信封投递进队列 | 不含业务规则 |
| **im-server** | 维护 WebSocket 长连接、消费队列、把消息投给在线的端 | **不碰数据库、不判断业务** |

### 最硬的一条边界:`im-server` 不依赖数据库

它需要的一切,要么来自队列里的信封,要么来自 Redis。任何"顺手在 server 里查一下表"的念头,都意味着这条边界已经破了,之后 schema 一改就得通知三方。

### 另一条容易被忽略的边界:`im-server` 不保证送达

推送是**尽力而为**。用户离线时投递失败是正常的,不需要 server 做重试或补偿——消息已经在 platform 落库了,客户端下次登录用 `loadOfflineMessage` 拉回来。**把这条写清楚,能省掉 server 一半的复杂度。**

## 2. 推送链路

### 私聊

1. 客户端 HTTP → `POST /message/private/send`
2. platform 落库(分配 `seqNo`),构造 `IMPushMessage`
3. platform 通过 im-client 投递:
   1. 查接收方连接位置:`HGETALL im:user:server:{recvId}` → 得到它连接的所有 `serverId`
   2. 对每个 `serverId` 执行 `LPUSH im:unread:{serverId}`(信封 JSON)
4. im-server 在自己那条队列上 `BRPOP`
5. im-server 在本机连接表里找到该 userId 的所有连接,**逐个下发**(多端在线就这么自然支持了)

### 群聊

1-2 同私聊,区别是信封里的目标是 `groupId`
3. platform 仍要先算出"该推给哪些 server":遍历群成员 → 逐个查连接位置 → 得到 `serverId` 集合
4. 每个涉及的 `serverId` 投一条信封
5. im-server 收到后决定推给本机哪些连接(**这里有个待确认项,见第 6 节**)

## 3. Redis 数据结构(契约)

### 3.1 推送队列

| 项 | 值 |
|---|---|
| key | `im:unread:{serverId}` |
| 类型 | **list**,当队列用 |
| 写 | im-client:`LPUSH` |
| 读 | 对应的 im-server:`BRPOP`(**只消费自己 serverId 的那一条**) |
| 内容 | `IMPushMessage` 的 JSON,**不带 Java 类型信息** |

### 3.2 用户连接位置注册表(多端在线的核心)

| 项 | 值 |
|---|---|
| key | `im:user:server:{userId}` |
| 类型 | **hash** |
| field | `ClientType.code`(1=web, 2=app, 3=h5, 4=小程序) |
| value | `serverId` |
| 写 | im-server(连接建立 `HSET`,断开 `HDEL`) |
| 读 | im-client(路由)、im-platform(判断在线状态)、im-server 自身 |

**约定:**

- hash 非空 ⇒ 该用户在线(这就是"在线状态"的数据源)
- 同一 `clientType` 重复登录**视为同一端**,后连接覆盖前连接;旧连接由 im-server 主动断开
- ⚠️ 断开时必须判断:**只有当本机已无该 `(userId, clientType)` 的连接时,才允许 `HDEL`**。否则"同一个浏览器开两个标签页,关掉一个"会把注册表删空,用户被误判为离线

### 3.3 控制事件队列

已存在于 `RedisKey`,目前无人使用:

| key | 谁写 | 谁读 | 用途 |
|---|---|---|---|
| `im:queue:user:banned` | platform | im-server | 用户封禁 → 强制下线 |
| `im:queue:group:banned` | platform | im-server | 群封禁 |
| `im:queue:group:unban` | platform | im-server | 群解封 |

### 3.4 群成员缓存

| 项 | 值 |
|---|---|
| key | `im:cache:group_member_ids`(hash:field=groupId, value=成员id集合) |
| 写 | **im-platform**(成员发生增删改时维护) |
| 读 | im-server(群发时用) |

⚠️ **这是 platform 的义务**。不维护它,im-server 群发时查不到成员,群消息直接发不出去。是否保留这个缓存取决于第 6 节第 1 个待确认项。

## 4. 推送信封 `IMPushMessage`

字段定义见 `im-common/.../model/IMPushMessage.java`,那里有逐个命令的字段约定表。

示例(私聊消息):

```json
{
  "cmd": 1,
  "chatType": 1,
  "sendId": 2,
  "recvIds": [3],
  "groupId": null,
  "timestamp": 1761234567890,
  "id": 1024,
  "localId": "1758600000123",
  "seqNo": 17,
  "recvId": 3,
  "type": 0,
  "content": "在吗",
  "sendTime": 1761234567800,
  "status": 0,
  "deleted": false
}
```

### 三条硬约定

1. **时间戳一律毫秒 long**。不要塞 `Date` 对象,避免时区与序列化差异。
2. **不要用 Jackson 的 default typing**(即 JSON 里不要出现 `@class`)。
   ⚠️ 这一条最容易踩:im-platform 的 `RedisTemplate` **开启了 default typing**。如果 im-client 图省事直接复用它来序列化信封,platform 的业务类名会被写进队列,im-server 反序列化时要么找不到类而失败,要么被迫依赖 platform 的业务模块——**直接破坏"im-server 不依赖业务"这条边界**。im-client 必须使用自己的、不带类型信息的 JSON 序列化器。
3. **协议传数字码,不传枚举名**。这样以后重命名 Java 枚举不会破坏协议兼容性(所以 `RedisKey`/`IMCmd`/`ChatType` 里都是 `code`)。

另外:字段**只增不删、只改不改义**;反序列化需配置为忽略未知字段,保证老版本能兼容新字段。

## 5. 义务清单

### im-platform 必须做

- **先落库、后推送**。保证消息不丢;推送失败不影响事务
- 群成员变更时维护 `im:cache:group_member_ids`(若保留该缓存)
- 封禁用户/群时往对应事件队列投递
- 推送新消息时 `deleted` 恒为 `false`(刚发出的消息对谁都没删)
- 提供 `loadOfflineMessage` 作为**离线兜底路径**(唯一可靠的送达方式)

### im-server 必须做

- 只消费自己 `serverId` 的那条队列
- 维护 `im:user:server` 注册表(含上面提到的 HDEL 判断)
- **不解析业务负载,原样转发**
- 不在本地保存任何业务状态

### im-client 必须做

- 用不带类型信息的 JSON 序列化器
- 投递前填好路由字段(`cmd` / `chatType` / `sendId` / `recvIds` / `groupId` / `timestamp`)
- **查不到连接位置时不要投递**(对方离线,消息留在库里等它下次拉取)

## 6. 待确认事项(需要三方拍板)

| # | 问题 | 说明 |
|---|---|---|
| 1 | **群发时信封里给不给成员列表?** | 给了:im-server 逻辑极简、platform 也不必维护成员缓存(义务少一项)。不给:信封小、一群一条,但 server 必须查成员缓存,且成员变更后缓存要即时更新,否则漏发/错发。**倾向"给"** |
| 2 | WS 握手鉴权 | 现状是客户端拿 platform 签发的 `accessToken` 直连 `8878`,server 用共享密钥本地验签(见 `im-server/application.yml` 注释)。若改为一次性 ticket,platform 需要新增签发接口 |
| 3 | `serverId` 如何生成 | 配置写死?还是 `IP:端口`?它同时是队列 key 的一部分,**必须全局唯一且稳定** |
| 4 | 队列用 list 还是 pub/sub | 现状(list,来自 box-im)可持久化,server 重启期间消息会堆积;pub/sub 会丢消息 |
| 5 | `im:cache:friend` 的归属 | 目前看不出谁读;若只有 platform 用,应标为 platform 私有,别放进契约 |
